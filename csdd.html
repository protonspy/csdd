Spec-Driven Development como contrato executável

Um único binário que transforma o workflow SDD do Claude Code de "boa intenção em markdown" num contrato validado mecanicamente — para humanos e agentes de IA.

O problema

Agentes de IA escrevem código rápido.
Rápido demais para sair sem contrato.

🎯

Escopo que escorrega

Sem requisito explícito e testável, o agente "interpreta" — e cada execução interpreta diferente. Não há linha de base para revisar.

🔗

Zero rastreabilidade

Código sem vínculo a um requisito. Ninguém sabe por que uma função existe nem o que quebra se ela mudar.

⚖️

Revisão humana tarde demais

O humano só vê o resultado no PR — quando reverter custa caro. A decisão deveria ser visível antes do código.

A resposta é SDD — Spec-Driven Development: uma camada de contrato (requisitos → design → tarefas) com aprovação humana em cada portão. O csdd é a ferramenta que torna esse contrato impossível de furar por acidente.

O que é o csdd

CLI + TUI num único binário Go

O único autor sancionado dos artefatos do workflow. Você não edita frontmatter, spec.json ou anotações de tarefa na mão — você gera de template, edita o corpo e valida.

🖥️ CLI — para agentes & automação

Driven por flags, headless. Expõe 100% das funções para que Claude Code, Cursor, Codex ou CI dirijam o binário sem ler o código-fonte.

csdd spec generate photo-albums --artifact requirements

⌨️ TUI — para humanos

Interface interativa (Bubble Tea). csdd sem argumentos abre wizards e navegador de artefatos. Mesma operação, mesmas regras.

csdd   # sem args → TUI interativo

🔑 Princípio central: as duas superfícies chamam os mesmos helpers de operação. Uma única fonte de verdade — o que o humano faz na TUI, o agente faz idêntico via CLI.

Modelo mental · leia isto primeiro

Duas distinções valem mais que tudo

📜 Specification — o contrato

Os requisitos, o File Structure Plan no design, e as anotações _Boundary:_ / _Depends:_ nas tarefas.

👤 Humanos revisam e aprovam isto.

🧩 Design — o espaço de implementação

Componentes, internos, sequenciamento dentro de cada tarefa. Como o contrato é cumprido.

🤖 O agente é livre aqui, depois da aprovação.

A segunda distinção são os phase gates: nenhuma fase é gerada antes da anterior ser aprovada por um humano — e isso é aplicado mecanicamente, não por convenção.

O ciclo de vida de uma feature

Da ideia ao pronto para implementar

# 1 · bootstrap (uma vez por repo)
csdd init --with-baseline

# 2 · cria o workspace da feature
csdd spec init photo-albums

# 3 · requirements → edita em EARS → valida → aprova
csdd spec generate photo-albums --artifact requirements
csdd spec validate photo-albums          # exit 2 = corrija o que ele apontar
csdd spec approve  photo-albums --phase requirements

# 4 · design (bloqueado até o passo 3 passar)  → 5 · tasks (idem)
csdd spec generate photo-albums --artifact design   # ... validate, approve
csdd spec generate photo-albums --artifact tasks    # ... validate, approve

✓ spec.json: ready_for_implementation = true   # implementação pode começar

💡 csdd spec status <feature> entre qualquer dois passos: fase + aprovações + issues de validação numa só tela.

As convenções que o validador exige

EARS & anotações de tarefa

📝 Requisitos em EARS

Sintaxe fixa, testável, uma behavior por critério. SHALL — nunca should. IDs N.M únicos.

### Requirement 1: Album Management
1. WHEN a user creates an album
   THEN the system SHALL persist it <500ms.
2. IF the name is empty
   THEN the system SHALL return 400.
3. WHILE deleting THE SYSTEM SHALL
   block new uploads.

✅ Tarefas anotadas (não é todo-list)

Cada folha rastreia requisitos; paralelismo é declarado e verificado.

- [ ] 2. AlbumService _Boundary: AlbumService_
  - [ ] 2.1 create / rename / delete
    _Requirements: 1.1, 1.2_
- [ ] 3. PhotoService _Boundary: PhotoService_ (P)
  - [ ] 3.1 upload S3
    _Requirements: 2.1_
    _Depends: 1.2_
_Requirements:_ toda folha _Boundary:_ todo (P) _Depends:_ entre boundaries

(P) = roda em paralelo. Dois (P) não podem compartilhar boundary — o validador rejeita, garantindo execução paralela segura por agentes.

🔴 Skill tdd-cycle

  • Um task de folha por invocação. Pega o ID em specs/<f>/tasks.md; não agrupa tasks "pra economizar".
  • O RED falha pelo motivo certo. Não vale erro de compilação — cita a falha antes de seguir.
  • Nunca enfraquece um teste para a suíte passar. Comportamento novo = novo RED.

✅ verify-change + Definition of Done

Antes de reportar concluído: roda os checks executáveis e produz evidência real — "compila" e "parece certo" não são done.

# a evidência colada no relatório / PR
go test ./...   ✓
lint            ✓
typecheck       ✓
build           ✓

Cada folha rastreia _Requirements:_ → o teste prova o requisito. Evidência vence asserção.

🔎 Review adversarial — skill pr-review

  • code-reviewer roda no diff; resolve todo Blocker antes de seguir.
  • security-reviewer se toca auth / secrets / input — resolve Critical/High.
  • Reviewers não escrevem — você aplica o fix e re-revisa até limpo.

✍️ /commit + pre-push gate

# Conventional Commits, gerado do diff + spec

Implements photo-albums; tasks 2.1, 2.2.

# git push → hook roda a suíte; vermelho BLOQUEIA

✗ pre-push: test gate failed — push blocked

Nunca commitar com Blocker aberto; nunca git push --no-verify. O PR carrega evidência: spec links · tasks concluídas · saída real dos checks · riscos.

Decisões de arquitetura que valem destacar

Quatro escolhas deliberadas

① CLI = TUI, sempre

As duas superfícies convergem nos mesmos helpers. Não existe função que só a TUI faz — por isso um agente headless tem 100% do poder.

② Templates embutidos

go:embed all:templates compila os templates no binário. Você baixa um arquivo e ele funciona offline, sem instalar nada.

③ Validação mecânica, não opinativa

O validador nunca pede julgamento: ou o critério começa com WHEN ou não. Determinístico → um agente confia no exit code.

④ Artefatos são texto puro

Tudo vira markdown/JSON versionável em .claude/ e specs/. Revisão acontece no PR, com as ferramentas que o time já usa.

Resultado: o CLI nunca te impede de fazer o certo — ele te impede de fazer o errado sem tornar a decisão visível. Furar um gate exige --force explícito, e isso aparece no histórico.

O que cada gate de validação pega

O validador é a rede de segurança

spec · requirements

  • Todo critério começa com WHEN/WHILE/IF/WHERE/THE SYSTEM
  • Nenhum usa should
  • Headers ### Requirement N: únicos

spec · design

  • Seções Boundary Map e File Structure Plan presentes
  • Todo ID de requisito aparece na tabela de traceability
  • design.md ≤ 1000 linhas (senão, divida o spec)

spec · tasks

  • Toda folha tem _Requirements:_ com IDs reais
  • Todo (P) tem _Boundary:_ que casa com o design
  • Nenhum par (P) compartilha boundary

skill · mcp · steering

  • SKILL.md ≤ 500 linhas / ~5k tokens; refs citadas
  • mcp: exatamente 1 transporte (stdio ou url)
  • steering: inclusion válido; fileMatch tem pattern

Exit codes: 0 ok · 1 erro de uso · 2 falha de validação. Scriptável em CI.

Como isto chega ao nosso dia a dia

Nativo do Claude Code — sem camada de conversão

O workspace que o csdd escreve já é o layout que o Claude Code espera. csdd init faz o bootstrap e cuida do wiring:

# layout nativo, escrito direto em disco
CLAUDE.md             # entry point + imports de steering
.claude/steering/*.md # @-referenciado no CLAUDE.md
.claude/agents/*.md   # sub-agentes (Read, Grep…)
.claude/skills/<n>/   # bundles de skill
.claude/commands/     # slash commands (/commit)
.claude/hooks/        # automação determinística
specs/<feature>/      # contratos SDD
.mcp.json             # servidores MCP

Criar um steering insere automaticamente @.claude/steering/<nome> num bloco gerenciado do CLAUDE.md — idempotente, nunca clobbera edições manuais.

O que o time ganha

  • Zero atrito com o Claude Code. Os artefatos são lidos nativamente — nada de exportar ou converter.
  • Revisão onde já trabalhamos. Specs e steering são texto em PR — diff, comentário, approve.
  • Menor privilégio por padrão. Sub-agentes nascem com Read, Grep; MCP com escopo restrito.
  • CI valida o contrato. Um csdd spec validate no pipeline barra spec quebrado antes do merge.
